- 8 個主要頁面的 h1/page title,用了 **7 種不同**的 size/weight 組合(`text-3xl` / `text-[28px]` / `text-[26px]`(x2 不同頁)/ `text-2xl` / `text-[22px]`,還有一處用 `font-semibold` 取代其他頁都用的 `font-bold`)。
- 同一個 `friends/page.tsx` 裡,同樣是 h2 區塊標題,「Add friend」用 `text-xl`,「Your friends」卻用 `text-3xl`。
- 找到 **~20 種**不同的文字大小數值(`text-xs` 到 `text-[40px]` 都有),遠超過一套排版量表該有的 6–8 級。

## 三、動畫/動態系統——沒有共用 Motion Token

- CSS `.module.css` 裡的動畫時長幾乎每個都是獨立數字:`260/320/340/420/460/520/620/700/900ms`,以及 Yumi/寵物的 idle loop 用了十幾種不同秒數(`2.1s ~ 5.2s`),看得出是憑感覺個別調的,不是一套「快/中/慢」分級。
- Easing 曲線至少 **11 種不同的 `cubic-bezier()`**,其中好幾組彈性強度非常接近(`0.34,1.2` vs `1.3` vs `1.4` vs `1.56`)——明顯是各自獨立調校,不是共用彈跳感。
- Tailwind 按壓回饋 `active:scale-90` / `active:scale-95` / `active:scale-[0.98]` 三種混用,連同一個資料夾(`components/vocabulary/`)裡都同時出現 90 和 95。
- **目前完全沒有 Motion Token 系統**:沒有 `tailwind.config`(Tailwind v4 設定在 `globals.css` 的 `@theme inline`),裡面只定義顏色/字型變數,沒有 `--duration-*` / `--ease-*`。
- Reduced Motion 支援度分裂:**Yumi 與寵物角色的 CSS 動畫做得很完整**(YumiFace、YumiMark、YumiHomeStage、CookieTray、MoodLogoSwiper、BottomNavigation、AppSplash、LogoLoader 都有對應 `.reduced`/`@media` 處理),但一般按鈕/卡片的 Tailwind `duration-*`、`active:scale-*` 完全沒有 `motion-reduce:` 變體——**規格書要求的「所有效果都要兼顧 Reduced Motion」目前只有吉祥物做到,一般 UI 微互動沒做到**。

## 四、i18n——字典本身很扎實,但有實際外洩點

好消息:`types.ts` / `en.ts` / `zh-TW.ts` 三份檔案的 namespace 結構完全對齊,沒有結構性漂移。

壞消息,以下是「明明同一個檔案其他地方都用 `t.*`,唯獨這幾行忘記」的具體外洩點:
- `ConversationThread.tsx`:`aria-label="Play English word"` 系列 5 處硬編碼、`<span>English</span>`/`<span>Traditional Chinese</span>` 硬編碼,甚至同一組按鈕裡一個 aria-label 是英文、旁邊一個是中文(`"Play English word"` vs `"播放中文單字"`,899 行附近)。
- `VocabularyList.tsx` 與其子元件(`VocabularyLoadingState/EmptyLibraryState/LookupResultState`):多處硬編碼英文提示文字。
- `VocabularyDetailSheet.tsx`:`Close/Edit word/Add to collections/Send to a friend/...` 全是硬編碼 aria-label。
- **整個登入/註冊/忘記密碼流程完全沒接 i18n**:`app/signup/page.tsx`、`app/(public)/login/page.tsx`、`forgot-password`、`reset-password`、`LogoutButton.tsx` 都沒 import `useTranslation`,即使 `lib/i18n/types.ts` 早就定義好完整的 `auth.login.*` 字典可用。這是規格書第十項「i18n 完整套用」裡影響最大的一塊。

## 五、錯誤處理外洩 / 死互動 / 安全區

**死互動(規格要求檢查的「點擊沒反應」)**:全 repo 搜尋 `onClick={() => {}}`、無 handler 的假按鈕、`TODO/FIXME` 註解,**完全沒有發現**——這部分是乾淨的,不用修。

**錯誤訊息外洩給使用者(這是實際問題,而且是系統性的)**:
有一個重複出現 ~20 次的 bug pattern:
```ts
setMessage(error instanceof Error ? error.message : friendlyCopy)
```
邏輯寫反了——JS/Supabase 的錯誤幾乎必然是 `Error` 實例,所以「友善訊息」那個分支永遠不會被執行,使用者看到的**永遠是原始技術錯誤訊息**,包括資料庫欄位名稱、Postgres 錯誤碼等。出現在:
`vocabulary/collections/page.tsx`、`vocabulary/collections/[id]/page.tsx`、`friends/page.tsx`、`review/page.tsx`、`CollectionPickerSheet.tsx`、`ConversationThread.tsx`、`ConversationList.tsx`、`NotesComposer.tsx`(共 8 個檔案、約 20 處)。
另外 `signup/forgot-password/reset-password/GoogleLoginButton/OnboardingFlow` 這幾處**根本沒有 fallback**,直接把 `error.message` 顯示出來。

**底部導覽列安全區**:多數頁面統一用 `pb-28`(112px,對應共用的 `Screen`/`AppPage` 元件),這是對的。但兩處例外比標準少留空間:
- `profile/page.tsx` 用 `pb-24`(96px,少 16px)
- `capture/page.tsx` 首屏空狀態用 `pb-16`(64px,少 48px,風險較低因內容置中,但仍不一致)

## 六、Yumi/Murphy 動畫架構

- 前端完全沒有任何地方叫「Murphy」——只有兩個 Supabase migration 檔名殘留 `murph_pet_state`,DB 層早就正名為 Yumi 了,前端一律叫 Yumi,這部分沒有命名混亂問題,規格書提到的「Murphy」在目前程式碼裡不存在,可能是舊稱呼的記憶,不影響修正方向。
- 目前有 **6 套各自獨立的吉祥物動畫實作**,共用同一顆基礎 SVG 外殼(`ExchangeNotesMark`),但眨眼/呼吸的 CSS keyframes 是分開手刻的:
  - `YumiMark`(Vocabulary 寵物,694 行 CSS,mood 驅動)
  - `YumiFace`(發音教學,389 行 CSS + 281 行姿態運算,phonetic 驅動)
  - `YumiHomeStage`(首頁,829 行 CSS,29 組 keyframes)
  - `LogoLoader`、`AppSplash`、`MoodLogoSwiper`(各自一套,較小)
- 眨眼動畫在 `YumiMark` 和 `YumiFace` 之間**逐幀數值完全相同**(已核對 44/46/47/50% 時間點與位移量一致)——證實是複製貼上而非共用,呼吸/漂浮動畫則是「神似但數值不同」。
- 架構上 `YumiFace` 是一套完整的「音素特徵 → 姿態運算 → SVG 渲染」pipeline;`YumiMark` 則是「心情字串 → CSS data-attribute → 對應 keyframe」的靜態對照表。**這兩者是本質不同的兩套設計,不是換個名字的同一套邏輯**——這代表規格書要的「共用 YumiAnimationEngine」沒辦法是單純合併檔案,需要設計一層能同時餵給「連續運算姿態」與「離散心情狀態」兩種消費者的抽象層,是這次規格書裡工程量最大的一項。
